## Production paths and causes

Canonical detail and Library use `RefreshChapterEvidence` and `ReconcileChapterEvidence`. Content selection and progressive discovery use `ResolveChapterContent`, `DiscoverReadableChapter`, and a targeted `RefreshChapterEvidence.executeForBinding` after a binding changes. Legacy Reader entry and source switching still use `RefreshCanonicalChapters`, `MihonChapterInventoryGateway`, and `ReconcileChapterInventory` to support Mihon's operational chapter records. The two reconciliation paths therefore remain distinct, though they now share the same conservative identity-and-volume candidate resolver. This avoids a known difference in matching decisions but is not yet a single authoritative production write path.

| Problem | Cause found | Correction and evidence |
| --- | --- | --- |
| Slow evidence refresh and partial-write risk | Each evidence upsert reread the whole title's evidence and wrote one row at a time. | `ReconcileChapterEvidence` stages a title snapshot and writes chapters plus evidence under one SQLDelight transaction; the Data repository batches stable-key updates. Injected failure rolls back both, and repeat refresh preserves IDs and raw metadata. [Measured query counts](TSUZUKI-CHAPTER-RECONCILIATION-BENCHMARK.md) changed from 602/3,002/6,002 to 203/1,003/2,003 at 100/500/1,000 already-known observations. |
| Wrong canonical ID for repeated chapter numbers in different volumes | Legacy inventory reconciliation kept only the first chapter per numeric identity; the probe discarded explicit volume. | `ParseCanonicalChapterVolume` records only unambiguous explicit numeric prefixes; both reconcilers use `CanonicalChapterCandidateResolver`. Explicit Vol. 2 selects Vol. 2; duplicate or unknown-volume candidates are not selected arbitrarily. Stable external keys retain their confirmed mapping on a later unqualified label. |
| Contradictory provider evidence | One reused provider key could change number or volume; choosing the first candidate hid the conflict. | Evidence from a changed stable key is rehomed while the old row and other-source evidence remain; independently supported chapters survive. Confirmation, provisional, and conflicted states remain separate. |
| Wrong read option for a requested chapter | `MihonContentProvider` accepted numeric fallback or an old mapped variant without enough volume validation. | Fallback rejects mismatched or mixed explicit volumes. Mapped options now reject conflicting stored volumes, malformed volume labels, and source keys whose current volume contradicts stored evidence. Groups of the same volume remain available. The provider-specific test uses only synthetic inventory and does not prove live availability. |
| Reader session loss during source replacement | Old history and some adjacent lookups occurred before replacement pages and navigation were fully prepared; a failed replacement could disturb session state. | Pages and navigation are prepared before publication; publication rolls back a partial state update. Empty/throwing loaders leave the previous chapter; a late callback from a retired viewer is ignored. The new page index clamps to the actual page count; the automatic first-page callback does not overwrite earlier canonical progress. The timer starts with publication. Old Mihon history is written afterward on a bounded best-effort job. |

No SQLDelight schema migration was added, and no existing user database was deleted or rebuilt.

## Open risks and next acceptance work

1. **Canonical-to-Mihon recovery:** canonical page/history writes precede the legacy projection, so a projection error does not undo the canonical write. There is no durable retry record for a failed legacy projection. The bounded old-history job can also time out or be canceled with the Reader ViewModel. Add injected-failure tests and a durable recovery mechanism before claiming complete history integrity.
2. **Single update flow:** legacy Reader inventory and evidence refresh still write through separate interactors. Their matcher is shared, but a complete caller migration and behavioral equivalence tests are still needed. Do not delete the Mihon adapter before these pass.
3. **Actual source switching on Android:** helper/unit tests and the offline navigation emulator ran, but no instrumented valid→empty, valid→exception, or valid→valid source switch against a fake readable extension ran. The current navigation fixture has no such source/content harness. A real-phone manual acceptance remains required. No distribution APK was published.
4. **Provider observations:** the historical One-Punch Man MangaDex pt-BR 169 raw entries versus 163 provisional UI rows lacks a title-correlated current raw inventory; this round did not establish whether filtering, duplicates, or missing early chapters caused the difference. The synthetic tests must not be used as a provider count. The Death Note manual link path needs a full targeted-refresh integration run, and current live availability was not checked. HTTP/CAPTCHA/timeout cannot be treated as definitive absence.
5. **Dandadan:** chapter identity/list tests do not diagnose cut or cropped page images. Reproduction needs the original image dimensions, displayed bounds, reader mode, device/Android version, and a redacted screenshot or recording; no original images were available in this run.
6. **Reader page policy:** on a source switch the requested page is clamped to the new source's last page, while persisted canonical progress is left intact for the automatic initial callback. Later user navigation can write a new page index; per-variant page-position semantics are still a design decision. The offline emulator reported page position as not observable.
7. **Extension cancellation:** Fast limits visible discovery waiting to 10 seconds. An extension that ignores cancellation can continue background work; an explicit cap on accumulated non-cooperative calls remains to be verified or implemented.

The branch is usable for the next integrity and device-validation slices. It is not yet an evidence-backed sign-off for the complete UI reformulation.
